    AGENTS.md 中文参考译本 —— 编码代理的仓库级执行契约¶

    译本性质：本文件是仓库根目录 AGENTS.md（对应本仓库版本 560dca6，2026-08-23）的中文参考译本，供人类读者理解仓库对编码代理的行为约束。 编码代理实际读取并执行的是英文原文——本译本不构成任何代理的指令来源；如有出入，以英文原文为准。 翻译约定：命令、路径、文件名、状态值与决策标签（如 READY、DONE、ADOPT、REJECT）保留英文原样；bash 代码块原样保留；正文叙述全部翻译。 关联：COLLABORATION.md（本仓库的协作与文档同步规则）· CLAUDE.md（导入英文原文的桥接文件）· progressive-disclosure-evals.zh.md（渐进式披露研究计划译本）

    项目意图（Project intent）¶

    book-to-skill 将书籍与文档转换为结构化、按需加载的 Agent Skill。仓库由职责截然不同的两半构成：

    1. 确定性的 Python 提取器（scripts/extract.py -> book_to_skill/）；
    2. 由 agent 执行的规格驱动生成器（SKILL.md）。

    除非有经过衡量的理由，不要模糊这两者的职责边界。

    事实来源（Sources of truth）¶

    改动代码之前，先阅读最小的相关文件集合：

    1. CONTRIBUTING.md —— 贡献规则与必需检查项。
    2. docs/architecture.md —— 当前架构与组件归属。
    3. SKILL.md —— 仅当改动涉及生成行为或生成技能的结构时才需要。
    4. SECURITY.md 与 SECURITY-NOTICE.md —— 涉及解析、文件、子进程、生成内容或依赖时。
    5. 与被改代码最接近的既有测试。

    对于渐进式披露（progressive-disclosure）研究/评估专项，还需阅读：

    • docs/research/progressive-disclosure-evals.md

    该文档是研究专项的执行台账，定义了任务顺序、证据门禁，以及哪些源自论文的想法仍属于假设而非产品需求。

    不可协商的规则（Non-negotiable rules）¶

    • 用测量说话，不要用断言说话。 任何关于质量、token、路由、准确率或成本改进的主张，都必须有可复现的证据。
    • 不要在假设的验证门禁通过之前，把论文假设变成生产行为。 特别地，不要仅因为"听起来合理"就添加 KEY_ELEMENTS 风格的元数据、library 模式、更深的路由，或新的 SKILL.md 内容。
    • 保持 SKILL.md 精简。 它是每次都会加载的转换器上下文。任何净增长都需要证据证明新增上下文物有所值。
    • 绝不提交受版权保护的书籍原文。 使用合成、公有领域或明确授权的 fixture。私有评估语料与原始 live 轨迹不得进入 git。
    • 评估工作避免引入新的运行时依赖。 仅用于评估的依赖必须留在核心运行时之外，且需给出理由。
    • 不要手工编辑 CHANGELOG.md。
    • 除非任务明确授权破坏性变更，保持向后兼容。
    • 不要为了让实验通过而削弱安全检查、路径加固、文本清洗（sanitization）或生成技能扫描。

    执行循环（Execution loop）¶

    任何非平凡任务都应使用以下循环。不要从想法直接跳到实现。

    1. 定向（Orient）
    2. 阅读本文件与相关的事实来源文件。
    3. 在提出新模块或新抽象之前，先查看现有代码与测试。

    4. 对于研究计划内的工作，定位第一个状态为 READY 且依赖已完成的任务。

    5. 规划最小连贯变更（Plan the smallest coherent change）

    6. 说明要解决的假设或缺陷。
    7. 说明什么不会被改动。
    8. 优先复用既有工具，而不是另起炉灶写平行实现。

    9. 在编辑代码之前先定义验收命令。

    10. 实现单个任务（Implement one task）

    11. 保持 diff 聚焦。
    12. 实现与确定性测试同步提交。

    13. 不要顺手重构无关代码。

    14. 证明它（Prove it）

    15. 运行任务专属检查。
    16. 运行下文的仓库门禁。

    17. 留存真实的命令输出或机器可读的结果工件；"看起来没问题"之类的话不是证据。

    18. 记录状态（Record state）

    19. 当研究计划在任务范围内时，更新研究计划中的任务状态/证据部分。

    20. 阻塞就如实记录为阻塞；绝不能因为"预期的代码写出来了"就把任务标记为完成。

    21. 门禁绿了才继续（Continue only after the gate is green）

    22. 只有当前任务被证明之后，才能进入下一个依赖就绪的任务。
    23. 遵守计划中定义的 PR 边界。改变生产行为的任务不得与无关的研究基础设施悄悄捆绑在同一个 PR 里。

    验证门禁（Validation gates）¶

    代码改动的最低本地检查：

    pytest -q
ruff check .

    如果 SKILL.md 发生改动：

    python3 tools/validate_skill.py SKILL.md

    如果提取行为发生变化，还需运行相关的提取器冒烟/复现命令及其定向测试。

    如果生成技能的行为发生变化，需提供改动前后的生成工件或基准结果来证明预期差异，且不得提交受版权保护的原文。

    任何必需检查被跳过、失败、或被未经验证的声明所替代，任务就不得标记为 DONE。

    评估工作的成本纪律（Evaluation-work cost discipline）¶

    Live 模型实验代价高昂，永远不能作为第一步验证手段。

    • 先跑单元/fixture 测试。
    • 大规模扫描之前，先做小规模判别样本。
    • 按 源/配置/模型/prompt 身份 做键，缓存并复用已生成的技能包。
    • live 运行之前，预先登记条件、语料、问题集、模型/harness、重复次数以及 token/成本上限。
    • 在较小规模的门禁给出理由之前，不要直接跳到 10/20 本书量级的扫描。
    • 如果存在更便宜的能证伪假设的测试，先跑它。

    指令作用域（Instruction scope）¶

    本根文件作用于整个仓库。更深层级的 AGENTS.md 可以为其子树添加更窄的指令；指令冲突时，以更具体的文件为准。用户/系统的直接指令优先于仓库指引。
