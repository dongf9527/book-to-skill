    Book-to-Skill 转换器¶

    把书面知识转化为可落地的 agent 技能——提取的是结构，不是摘要。

    设计哲学（Philosophy）¶

    书籍中沉淀着专家经验：框架、原则与技巧，往往经年累月才打磨成形。本技能把这些知识提取成 GitHub Copilot CLI、Amp、Claude Code、Hermes Agent、OpenCode、OpenClaw 或其他兼容 agent 可以反复调用的形式。

    提取结构，而非摘要。 技能不是读书报告。它是一套工具箱：

    • 具名框架（有明确应用场景的思维模型）
    • 可行动的原则（指导决策的规则）
    • 技巧（分步方法）
    • 反模式（要避开什么、为什么）
    • 作者语气校准（作者如何思考与表达）

    保留作者的精确表述。 框架的命名往往有特定理由。"The 5 Whys（五问法）"不能替换成"多问几次为什么"。要捕获原文的准确提法。

    分层控制深度。 简单的书 → 简单的技能。含 10+ 框架的复杂书 → 带参考文件与按需章节的技能。

    运行模式（Modes of Operation）¶

    四条路径。按用户的请求路由：

    1. 完整转换（默认）¶

    触发：用户给出一或多个文档/目录/glob 路径，无特殊指示 动作：执行下列全部步骤（Step 0–9） 输出：完整技能，含 SKILL.md、chapters/、glossary、patterns、cheatsheet

    2. 仅分析（Analyze Only）¶

    触发：用户说"分析一下""先只提取"，或"生成前我先审一遍" 动作：执行 Step 0–3，然后产出结构化提取报告（找到的框架、原则、技巧）。到此停止——不要生成技能文件。 输出：供用户审阅的分析报告

    3. 从既有分析生成（Generate from Prior Analysis）¶

    触发：用户已有分析笔记，或之前跑过"仅分析" 动作：跳过 Step 0–3，以所提供的分析为输入，执行 Step 4–9 输出：基于该分析生成的技能文件

    4. 更新/并入（Update / Fold-in，针对既有技能）¶

    触发：用户提供一或多个新源路径，并表示要更新既有技能（指向既有技能文件夹、给出 SKILLS_HOME 中已存在的技能 slug，或明确要求更新） 动作：执行 Step 0（范围外检查）、Step 1（校验输入）、Step 1.5（识别内容类型）与 Step 2（提取新文件），然后跳到 Step 5（定位/探测既有技能路径），按更新/并入工作流把新内容合并进既有技能文件。 输出：更新后的既有技能，含新增/修订的章节摘要与合并后的索引/词汇表。

    4. 项目级 Copilot 技能：.github/skills/

    10. Hermes Agent 项目技能：.hermes/skills/ 或 .agents/skills/

    12. OpenClaw 项目技能：.agents/skills/ 或 skills/

    Step 0 —— 范围外检查（Out-of-scope check）¶

    如果没有提供任何参数，停止并回复：

    "book-to-skill 需要一个受支持的文档路径、文件夹或 glob 模式。用法：book-to-skill <path-to-document-folder-or-glob>... [skill-name-slug]"

    在整个工作流中：

    • 先确定目标根目录。 在任何既有技能查找之前，先确定本次运行会写到哪里：按 Step 5 的表格与选择规则，取用户所用宿主的个人根目录或项目级根目录——项目级请求使用其项目级根目录，绝不写个人根目录。下文所说"已解析的根目录"（the resolved root）即指该目标。
    • 识别输入路径与可选的技能 slug。
    • 若最后一个参数不是存在的文件/文件夹、也不是能匹配到文件的 glob，且形如技能 slug（小写连字符、字母数字），则把它当作 SKILL_NAME。
    • 其余参数全部视为 INPUT_PATHS 列表。
    • 若任一输入路径本身就是技能目录（含 SKILL.md 与 chapters/ 子目录），或 SKILL_NAME 与已解析根目录中的既有技能 slug 匹配，则把本次运行标记为更新/并入（Mode 4）。
    • 重跑防护。 开始完整转换的提取之前，按 Step 5 的命名规则推导候选 slug——"作者-概念"形、"书名"形、以及用户给定的 SKILL_NAME——并在已解析根目录中检查是否已有匹配。命中即停止并询问用户："<skill-name> 已存在。请选择：(1) 更新/并入（Mode 4），(2) 校验既有技能的完整性后停止，或 (3) 强制完整重建。"用户选择之前不得重新提取。运行中断后恢复上下文时（网络断开、对话重放或续接），仅当上次运行报告的提取工作目录（其输出中的 Workdir -> 路径，或你在 BOOK_SKILL_WORKDIR 中设定的路径）仍完好、且仍与本次输入和选项匹配时才可复用——目录存在、其 metadata.json 可读、所列 sources 与本次转换的文件在文件名与内容指纹上一一对应（提取器在 metadata.json 中为每个源记录 sha256；对每个文件按当前状态重算指纹并要求精确匹配——book_to_skill/utils.py 中的 reuse_is_safe() 就是这一检查的可执行形态）、且其记录的 extraction_mode 与本次使用的模式一致（即 Step 2 的"确认提取的确实是你要的那份文档"规则）。若目录缺失（临时目录被清理）、metadata.json 不存在、sources 不再匹配（文件名不同或内容指纹变化）、记录的 metadata 中某源没有 sha256（指纹机制引入之前记录的，无法确认新鲜度）、或模式不一致——如实说明并改为重新提取，不要续用。拿不准时，先问用户再决定丢弃还是续用。

    Step 1 —— 校验输入（Validate input）¶

    确认 INPUT_PATHS 中至少有一个受支持的文件、目录或 glob 模式。 对目录与 glob 进行展开，找出匹配的受支持文件（.pdf、.epub、.docx、.txt、.md、.markdown、.rst、.adoc、.html、.htm、.rtf、.mobi、.azw、.azw3）。

    找不到受支持文件时，停止并给出清晰的错误信息。

    Step 1.5 —— 识别内容类型（Identify content type）¶

    提取之前，询问用户：

    "这些源文件属于哪类内容？这能帮我选择最合适的提取方法。

    1. 技术类（Technical）——含代码块、表格、公式、图示（如编程书、学术论文、架构指南）
    2. 文本为主（Text-heavy）——以散文为主，几乎没有表格/代码（如管理、效率、叙事非虚构）
    3. 不确定——我会用快速方法，若质量受限会提示你"

    把回答存为 BOOK_TYPE：

    • 选项 1 → BOOK_TYPE=technical
    • 选项 2 → BOOK_TYPE=text
    • 选项 3 → BOOK_TYPE=text

    若 BOOK_TYPE=technical，先告知用户：

    "📐 已选择技术模式——使用 Docling 做结构感知提取（表格、代码块、公式保存为 markdown）。每页约 1.5 秒，较长的源文件预计需要几分钟。现在开始……"

    若 BOOK_TYPE=text，告知：

    "📄 已选择文本模式——对每种文件类型使用最快的可用提取器。纯文本/Markdown/HTML 通常几秒就绪；PDF 在可用时使用 pdftotext。"
