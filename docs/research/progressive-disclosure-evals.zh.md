## 1. 为什么要有这项工作

仓库已有 `tools/discovery_tax.py`，它用真实提取出的章节体量来建模上下文成本。该工具有用，但它自己的文档也如实说明：discovery-loop 的数字是**模型值**，不是对真实 agent 轨迹的测量。

因此，下一步有价值的动作不是再提出一个省 token 的主张、也不是再造一个生成特性，而是建立一个小型评估系统，能用证据回答：

1. agent 是否找到了正确的源/书/章节；
2. 到达正确材料之后，表示（representation）是否帮得上忙；
3. agent 用了哪些文件/工具；
4. 这次运行花了多少 token/调用次数；
5. 在相同条件下，一个拟议变更能否胜过现有行为。

只有拿到这些测量之后，源自论文的想法才可以改动生产环境的 `SKILL.md` 行为。

## 2. 论文支持了什么，什么仍然悬而未决

### 本文允许引用为"论文已支持"的内容

以下各条可以作为被引实验的发现来对待，同时保留论文自身的适用范围限制：

- 作者评估的是**基于 book-to-skill 的受控配方（recipe）**，不是本仓库当前完整的生成器。该配方按文档结构分块（回退值约 4,000 词），生成短摘要加 `KEY_ELEMENTS`，再路由到原始分块文本。
- 在研究总体中，单层/扁平（flat）技能包是最好的默认选择；把分块描述塞进常驻加载的子技能里会制造上下文压力，甚至造成伤害。
- 渐进式披露的价值取决于 harness。单本书场景下，像被测 Codex 配置那样强的导航者可以自己重建 `grep -> 定位 -> 读取`，从而削弱预构建技能包的准确率收益。
- 在多本书规模上，特别是在被测配置的英文开放问答中，扁平披露比裸导航退化得更慢。
- 论文的 `KEY_ELEMENTS` 字段**被使用了**，但其独立贡献**没有被消融（ablate）验证**。
- 论文**没有**验证当前 `book-to-skill` 的语义表示：框架、思维模型、反模式、决策规则、术语表/模式/速查表以及现行章节模板都不是实验的自变量。
- 论文明确没有确立向代码、技术手册或其他非叙事语料的迁移。
- 诸如 K=20 En.QA 条件下 `68.3M` 对 `32.5M` token 的成本对比，是特定条件下未命中缓存的测量值，不是普适的"省一半"结论。

### 来自附录的重要细微差别

不要把"层级永远没好处"这句口号编码成产品不变式。论文附录里存在任务/规模特定的格子，在那些条件下更深的路由能追平甚至领先（例如部分 Pi 开放问答条件）。稳妥的设计结论是：

> **扁平是要被打败的默认项。更深的路由是一个实验对象，既不是被禁止的架构，也不是生产必备项。**

### 本仓库的开放问题

在本文产出证据之前，以下均为假设：

- 相比论文式的 `摘要 + 关键元素 + 原始分块` 表示，当前的结构化表示能否改善**应用/决策**类任务？
- 加入精确路由词/实体，带来的路由改善是否足以抵消额外的常驻/激活加载上下文成本？
- 显式/强制激活能否把"路由失败"与"表示/推理失败"分离开？
- 论文观察到的规模规律，在技术书籍、文档或 SOP 类材料上能否复现？
- 库（library）级索引对真实的 `book-to-skill` 收藏是否有用？
- "结构化章节 + 可访问源证据"是否优于"仅结构化"或"仅原始文本"？
- 在路由与表示都受控之后，不同的分块粒度还重要吗？

## 3. 研究规则：保持因果问题可分离

不要在同一次对比里改变多个设计轴。使用如下分解：

```text
SOURCE
  -> CHUNKING
  -> ROUTING METADATA
  -> DISCLOSURE DEPTH
  -> ON-DEMAND REPRESENTATION
  -> HARNESS ACTIVATION/NAVIGATION
  -> ANSWER/DECISION
```

一个有效的实验只改变一个被关注的轴，其余轴在 harness 允许范围内保持固定。

示例：

- 测试**表示**：分块边界与路由索引保持一致，只改变路由命中后打开的载荷（payload）。
- 测试**路由元数据**：分块载荷保持一致，只改变索引元数据。
- 测试**激活**：技能包保持一致，在 harness 支持的前提下，对比自动发现与显式激活。
- 测试**分块**：路由/表示配方固定，只改变分块边界。

如果 harness 无法把某个变量固定住，就把混杂因素记录下来，而不是声称实现了因果隔离。

## 4. 成本纪律：每一次更贵的运行，都必须对应一个它能改变的决策

每次 live 模型运行之前，必须有预运行配置/清单（manifest），包含：

- 源/语料 ID 与哈希；
- 条件名；
- 问题集 ID 与哈希；
- 模型与 harness；
- 若与作答模型不同，还需生成模型标识；
- prompt/配置哈希；
- 受支持时的重复次数/种子信息；
- `max_calls`；
- `max_input_tokens`；
- `max_output_tokens`；
- 可选 `max_cost_usd`（仅当运营方提供了当前定价）；
- 本次运行有必要进行的理由，以及它能改变的决策。

运行器必须在触及配置的硬上限时停止，而不是悄悄超出。

任何新实验的运行顺序：

1. 单元测试 / fixture 回放；
2. 一个或少数几个冒烟问题；
3. 最小判别语料；
4. 仅当方差/不稳定性有要求时才重复运行；
5. 只有当较小规模运行给出了继续的理由，才扩大 K 或扩大扫描范围。

绝不要以 20 本书量级的扫描开局。

当 源/配置/模型/prompt 身份 一致时，应复用已生成的技能包。不要为重新生成完全相同的输入付费。

## 5. 规划中的仓库形态

以下是目标形态，不是已存在的代码。任务可以随仓库演进调整路径，但偏离之前必须先更新本计划。

```text
tools/evals/
  manifest.py          # stable run manifest + hashes + budget fields
  score.py             # deterministic metrics where possible
  replay.py            # replay recorded/synthetic trajectories without APIs
  paper_flat.py        # paper-style baseline pack builder
  run.py               # experiment orchestration / dry-run / budget gate
  adapters/            # live harness adapters, added only when justified

tests/evals/
  ...                  # deterministic unit/integration tests

evals/
  fixtures/            # synthetic/public-domain/licensed tiny fixtures only
  configs/             # committed experiment configs, no secrets
  results/             # small aggregate summaries/manifests only

.eval-work/            # local raw trajectories, generated packs, private corpora; gitignored
```

评估代码不得成为 `book-to-skill` 的运行时依赖，除非后续的生产决策明确把其中一部分提拔为产品组件。

## 6. 核心指标

不要把实验简化成"最终答案准确率"。记录 harness 暴露的一切，包括：

### 路由/导航

- 技能被发现/被激活（在可观测时）；
- 选定的目标书；
- 选定的目标章节/分块；
- 打开的文件；
- 到达目标之前打开的无关文件；
- 工具调用（可观测时的 `grep`、读取/打开、搜索等）；
- 到第一条相关证据所花的时间/调用次数。

### 结果

- 存在金标准答案时的精确/确定性答案得分；
- 应用/决策类任务的任务专属量规（rubric）结果；
- 在给出错误答案之前，是否已到达正确的源证据。

### 效率

- 输入 token；
- 输出 token；
- 总调用次数；
- 可比时的耗时；
- 仅当定价连同日期/来源被显式记录时，才给出当前估算的货币成本；
- 若宿主暴露了缓存命中，缓存与未缓存的用量分开记录。

### 表示诊断

当"正确分块已被打开但答案错误"时，只在可观测证据支持的情况下分类：

- 证据在场，但推理/作答失败；
- 结构化表示遗漏了必需的证据；
- 路由选错了材料；
- 未知/无法判定。

不要从答案字符串反推隐藏的推理过程。

## 8. 任务规格

### PD-00 —— 冻结当前基线与评估契约

**目标**

在编写新的评估基础设施之前，先固化一个零 API 调用的基线快照。

**必需动作**

1. 运行当前仓库检查。
2. 在许可安全的 fixture 或现有的允许本地源上运行/检视 `tools/discovery_tax.py`（如有）；不得提交受版权保护的原文。
3. 记录当前工具"测量了什么"与"建模了什么"。
4. 从 `docs/architecture.md` 与 `SKILL.md` 记录当前生成器架构，但不改动二者。
5. 选定一个微小的合成/公有领域 fixture 集，用于确定性的评估开发。

**验收**

```bash
pytest -q
ruff check .
python3 tools/validate_skill.py SKILL.md
```

外加一份入库的小型基线说明/manifest，其中不含任何受版权保护的原文材料，并清楚标注"建模值"与"测量值"。

**不要**在本任务中改动生产生成行为。

---

### PD-01 —— 确定性的运行 manifest、哈希与预算

**目标**

让后续每一个结果都可归因、可复用。

**最小字段**

- schema 版本 / 运行 ID；
- 源 ID + 内容哈希；
- 条件；
- 问题集哈希；
- 模型/harness 标识；
- prompt/配置哈希；
- 种子/重复次数字段，不适用处显式标注 `unsupported`；
- token/调用/成本上限；
- 代码版本/commit SHA（可得时）；
- 工件/结果路径。

**要求**

- 除非证明确有必要，只用标准库实现；
- 序列化稳定；
- 确定性的哈希测试；
- 入库 manifest 不含密钥；
- 必填字段缺失/非法时清晰报错。

**验收**

定向测试证明：相同输入生成相同身份，有意义的配置变化会改变身份。全量 `pytest -q` 与 `ruff check .` 通过。

---

### PD-02 —— Fixture/回放评分器

**目标**

在不花费模型 token 的前提下，证明评分与轨迹记账的正确性。

使用微小的合成轨迹来代表以下情形：

- 正确路由 + 正确答案；
- 错误的书/章节路由；
- 到达正确证据 + 错误答案；
- 到达目标之前打开多个无关文件；
- 观测缺失/未知。

**输出**

机器可读的聚合结果与逐问题结果。评分器不得猜测未被观测的状态。

**验收**

测试覆盖上述每一种分类以及 token/调用聚合。回放命令在重复运行时产出稳定的 JSON。

---

### PD-03 —— 论文式扁平基线构建器

**目标**

创建一个与论文*实验表示*足够接近、可用于受控对比的可复现基线——但不假装它就是本仓库当前的生成器。

**基线结构**

- 一个根 `SKILL.md`；
- 用于发现的书级描述；
- 激活时分块路径 + 短描述的表格/索引；
- 索引中每个分块的 `SUMMARY` 与可选 `KEY_ELEMENTS` 元数据；
- 按需加载的原始分块载荷文件；
- 按源结构分章，并带显式回退策略。

摘要/KEY_ELEMENTS 的生成在 live 模式下可能需要模型；测试必须使用固定的 fixture 输出，以保证 CI 离线且确定。

**关键规则**

不要把这种表示加进生产 `SKILL.md`。它是实验基线。

**验收**

给定相同 fixture 与固定元数据，构建器输出稳定，且恰好只有一层路由。测试验证不引入子技能层级。

---

### PD-04 —— 运行器契约 + 首个 live harness 适配器

**目标**

在相同的问题/配置包络下运行 `raw`、`paper-flat` 以及一份提供/冻结的当前 B2S 技能包，并记录可观测的轨迹/成本数据。

**选择适配器之前**

先检视可用的上游工具。若某个既有 agent 协议/环境（例如 ACP/LOONGDOC，如果可访问且可复用）能用，优先与其兼容，而不是发明一套专属 harness。

**运行器必须支持**

- `--dry-run`：给出计划中的条件/调用/预算，且不做任何模型调用；
- 在宿主用量数据允许实施的前提下，硬性调用/token 预算门禁；
- 位于 git 之外的本地工作目录；
- 一次只跑一个条件；
- 即使受控失败也要产出结果/manifest；
- 适配器能力声明（打开的文件可观测？激活可观测？token 可观测？支持强制激活？）。

**验收**

先让 fixture/回放适配器变绿。然后才允许在申报预算内进行一次刻意极小的 live 冒烟运行。不做大规模扫描。

---

### PD-05 —— 表示实验（最高优先级研究问题）

**问题**

在路由受控的前提下，当前结构化的 `book-to-skill` 载荷，是否比原始章节文本或简单表示更能帮助 agent *应用*知识？

**条件**

源、分块边界、根路由元数据、harness、模型、问题与激活条件全部保持一致，只改变按需载荷：

1. `RAW_CHUNK` —— 原始分块文本；
2. `SIMPLE` —— 简单摘要表示；
3. `B2S_STRUCTURED` —— 当前的结构化章节表示；
4. `B2S_STRUCTURED_WITH_SOURCE_FALLBACK` —— 结构化表示外加源证据访问，仅当 harness 能在不改变路由的前提下完成这一对比时。

如果条件 4 无法被干净地隔离，宁可推迟它，也不要污染主对比。

**任务族**

使用能区分表示类型的问题：

- 事实检索；
- 解释/理解；
- 向场景迁移的应用；
- 使用源判据的决策/权衡；
- 反模式/反例。

**晋升规则**

单一数据集/格子不产生任何生产主张。按任务族分别记录效应与方差。零结果（null result）也是有效结论。

---

### PD-06 —— 自动激活 vs 显式激活

**问题**

失败中有多少来自"发现/路由到技能"，有多少来自"技能就位之后使用知识"？

在以下条件下运行相同的技能包/问题：

- `AUTO` —— 正常的宿主发现/激活；
- `FORCED` —— 显式激活/提供正确技能，**仅当 harness 支持干净的强制条件时**。

如果强制激活不被支持，就把适配器能力标记为 false，并且不得在未记录差异的情况下模拟一个"据称等价"的机制。

**输出**

在可观测性允许的范围内，把路由/激活成功与下游作答表现分开。

---

### PD-07 —— 路由元数据消融

**问题**

哪些元数据配得上它的上下文成本？

保持分块载荷与边界一致。按顺序比较：

1. `SUMMARY_ONLY`；
2. `SUMMARY_EXACT_TERMS`；
3. `SUMMARY_KEY_ELEMENTS`（论文式）；
4. `CURRENT_B2S_INDEX`，或它的一个精确定义投影。

同时记录路由成功与元数据 token 开销。

**要点**

`KEY_ELEMENTS` 不是已被验证的生产需求。本实验之所以存在，正是因为论文没有隔离它的效应。

**生产门禁候选**

只有当改善在多于一个恰当语料/任务族上重复出现、且新增上下文成本被如实报告时，才考虑增加/更改路由元数据。否则维持现状。

---

### PD-08 —— 技术/非叙事语料复现

**问题**

论文中有效的那些效应，能否迁移到 `book-to-skill` 最常被设计来结构化的材料上：技术书籍、文档、标准与 SOP 类内容？

**语料要求**

- 公有领域、宽松许可、合成或明确授权；
- 在得出产品结论之前，至少覆盖两种不同的结构/内容类型；
- 避免把著名材料当作唯一基准——参数记忆会掩盖检索/导航失败。

路由测试在可行时优先使用留出/合成的事实。

**验收**

运行既已定义的条件；复现期间不添加新特性。发布在法律上可安全入库的聚合 manifest/结果。

---

### PD-09 —— 库规模扩展

**问题**

对真实的非叙事 `book-to-skill` 材料而言，收藏级索引从什么时候开始变得有用？

不要先在生产中实现 `library-to-skill`。

实验条件可以包括：

1. 无库索引；
2. 每源一行的索引，类似论文的 `corpus-index.md` 设置；
3. 更丰富的语义库索引，仅在条件 2 完成测量之后。

**规模纪律**

从 K=1 与 K=5 开始。只有当较小规模运行留下未解决的规模问题、或出现有意义的分化时，才进入 K=10。进入 K=20 必须有书面理由与预算。

**生产门禁候选**

只有当索引在真实目标领域语料上提供了可复现的收益、而不只是把过量上下文搬进常驻加载层时，库特性才站得住脚。

---

### PD-10 —— 可选的混合 RAG 参照基线

**目标**

提供一个外部检索参照，不是运行时特性。

论文的参照栈是 BM25 + BGE-M3 稠密检索 + 倒数排名融合（reciprocal-rank fusion）+ BGE 交叉编码器重排。只有当 agentic 条件已经足够稳定、这一对比能回答一个决策时，才复现或复用该栈。

**规则**

- 把重型 ML 依赖限制在评估侧；
- 优先使用独立的可选环境/requirements 文件；
- 不得以这个基线主张"Skills 胜过 RAG"；
- 报告检索器/嵌入/重排器的确切版本与预算。

如果本任务的维护成本超过其决策价值，可以显式标记为 `REJECTED` 并附理由。

---

### PD-11 —— 分块消融

仅在表示/路由测试稳定之后运行。

比较一个小集合，例如：

- 源章节/小节边界；
- 保留段落边界的定长分块；
- 结构感知的技术小节（仅当提取器能可靠暴露时）。

路由元数据配方与载荷表示保持恒定。不要同时改动提取、路由与表示。

### PD-12 —— 证据评审与生产决策

这不是编码任务。它是决定任何实验想法能否进入产品的门禁。

对每个候选项，写出以下结论之一：

- `ADOPT` —— 证据足以支撑一个聚焦的生产 PR；
- `KEEP EXPERIMENTAL` —— 在某些区间有用，但不是安全的默认项；
- `REJECT` —— 未展示出价值，或成本/复杂度不可接受；
- `INSUFFICIENT EVIDENCE` —— 需要更多数据，并写明缺少的具体对比。

候选决策：

| 候选生产想法 | `ADOPT` 之前的最低证据 |
|---|---|
| 加入精确词项 / KEY_ELEMENTS 式路由元数据 | PD-07 的重复收益 + 上下文开销已测量 |
| 更改章节表示/模板 | PD-05 的任务族收益，且无可接受的检索退化 |
| 加入显式库模式/索引 | PD-09 的目标领域规模收益 |
| 加入更深/自适应层级 | 在计入上下文成本后仍胜过扁平的、特定任务/规模的重复收益 |
| 把生成/评估 manifest 加进常规产品输出 | 评估工具链之外已展示的用户/可复现性价值 |
| 作出 RAG 优势主张 | **永远不许普适化**；只能是带确切设置的、条件特定的基准表述 |

任何被采纳的特性都要有自己聚焦的 PR，带新测试与改动前后证据。不要在 PD-12 本身里同时改动多个生产面。

## 10. 主张护栏（Claims guardrail）

在证据变化之前，**不要**把以下说法发布出去或编码为既定事实（保留英文原文以便逐字对照）：

- "The paper validated the full current book-to-skill generator."（论文验证了当前完整的 book-to-skill 生成器。）
- "KEY_ELEMENTS improves routing."（KEY_ELEMENTS 改善路由。）（它被使用过，但未被独立消融验证。）
- "book-to-skill uses 2x fewer tokens."（book-to-skill 少用一半 token。）（被引的约 2 倍结果只是 K=20 En.QA 的一个特定条件。）
- "Skills beat RAG."（Skills 胜过 RAG。）（论文只是在特定任务下对比了一个特定的混合基线。）
- "Flat always beats hierarchy."（扁平永远胜过层级。）（扁平只是总体上最好的默认项；附录效应是任务/规模特定的。）
- "The results apply to technical books/code."（结果适用于技术书籍/代码。）（论文明确把非叙事迁移留作开放问题。）
- "Structured frameworks/mental models/anti-patterns are better than summaries."（结构化的框架/思维模型/反模式优于摘要。）（这正是 PD-05 要回答的问题。）

稳妥的表述必须点名具体条件，或者承认问题仍然开放。

## 12. 完成的定义（Definition of complete）

只有满足以下各条，本研究专项才算完成：

1. 确定性评估基础设施已存在并经过测试；
2. 至少一个真实 harness 在受控条件下产出可检视的轨迹/成本结果；
3. paper-flat 与当前 B2S 的对比已在合法/恰当语料上运行；
4. 在 harness 支持范围内，路由与表示已被分离；
5. 已尝试技术/非叙事语料复现；
6. 库规模扩展要么已被测量，要么被明确判定为不值得其成本而拒绝；
7. 每个生产候选项都得到了 `ADOPT / KEEP EXPERIMENTAL / REJECT / INSUFFICIENT EVIDENCE` 之一的决定；
8. 任何被采纳的行为都在独立聚焦的 PR 中实现，并带测试/证据；
9. 公开主张只更新到测量实际支持的程度。

成功标准**不是**"所有提议的特性都上线"。成功标准是：我们能够识别哪些想法配得上它们的复杂度，哪些不该进入 `book-to-skill`。
